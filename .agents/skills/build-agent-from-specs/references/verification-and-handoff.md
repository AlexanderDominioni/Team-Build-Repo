# Verification and handoff

Use for each implemented feature group and again for the complete application. This is an acceptance check, not a requirement for an arbitrary test count or exhaustive testing of framework internals. Scope each checkpoint to the current group and affected earlier behavior, then perform final cross-group reconciliation.

## Establish evidence of a working agent

Reconcile the feature acceptance ledger against the user-confirmed source baseline, not only task names. Each required trigger, branch, human interaction, and output needs its implementation location, UI route where applicable, durable result, and observed acceptance evidence. Automated features can have no UI action, with a reason recorded. Track implemented, connected, and verified separately. A shared journey may cover multiple requirements, but one happy-path result cannot stand in for unexercised branches. Make unavailable services and untested live behavior explicit. An HTTP 200, successful compilation, or simulated response alone does not establish that the agent workflow works.

Start with isolated fixtures and contract tests. When the approved plan includes live connection tests, run only their allowed scope and budgets. Do not perform a real payment, send, submission, deletion, or record change merely to make an end-to-end test look complete. Exercise such boundaries through an approved sandbox or dry-run path and report what was and was not executed.

For task-specific model choices, keep the comparison table and sources with the decision record. Verify the chosen model or classifier produces the required output from representative task inputs; a general benchmark does not establish that it performs best for this task. For learned classification/prediction, compare against a suitable baseline on held-out labeled outcomes, using metrics relevant to the decision and class balance, and prevent training/test or temporal leakage. If labels, execution access, or approved test budget are missing, report the unverified suitability without fabricating accuracy. For API/MCP choices, verify the particular operation and runtime route rather than assuming feature parity from a shared provider name.

## Select meaningful scenarios

Use the normal and exceptional paths present in the approved workflow. Common checks, when applicable, are:

- A normal trigger travels through the intended tasks and shows the source-backed result, not a hard-coded placeholder.
- Required missing input creates the intended question or error; unknown and zero remain distinguishable. A valid empty result is not mislabeled as a failure.
- A second run or a repeated UI click does not duplicate a side effect or lose existing state.
- A human question survives a page reload, is answered for the correct case, and follows the specified resume/new-run rule. An unauthenticated or stale review request cannot approve a different artifact version.
- A model proposing a forbidden tool, invalid arguments, or premature approval is rejected by the backend. Tool and inference limits remain enforced through failures and retries.
- A timeout, provider failure, MCP disconnection, or uncertain write yields the right status and handoff instead of fabricated success.
- L1 stays deterministic, L2 follows its fixed model-supported operation, and L3 can choose among permitted subtasks as evidence changes, without exceeding its authority. Validate observable outputs and decisions; do not expose or require private chain-of-thought.
- Results can be read back from the intended storage. For a hosted app, verify the deployed storage/runtime rather than assuming local files carried over.
- For GitHub Pages, verify the deployed repository base path, asset loading, navigation and direct-link refresh; inspect the published bundle for secrets/private records. Test the actual browser-to-backend path and user isolation when configured, plus restart/persistence and scheduler behavior required by the design. Follow [GitHub Pages delivery](github-pages-delivery.md); a static page loading cannot establish that external services work.
- For a local app, exercise the supplied launcher, readiness check, reopening an already running instance, documented shutdown and restart, and persistence of required saved state. Verify the browser-to-local-controller path and show readable errors for missing configuration or unavailable services. Test only the user's target platforms; report untested platforms explicitly. These checks do not authorize extra live API calls.
- UI controls reach the implemented backend; loading, error, review, and completed states are usable with keyboard and narrow-screen layouts. Animation respects reduced-motion preferences.
- A fresh user can enter or replace required context and discover all permitted actions, including conditional preparation/review controls before results exist. Sample initialization is not the only way to use the application unless a demo-only scope was requested.
- An empty or failed live run shows the actual empty/error outcome, with no sample fallback. Independent items continue after a failed item only when the approved workflow allows it.
- Public assets, logs, exports, and source changes exclude secrets and unauthorized private documents. Synthetic labels are still visible where synthetic content is used.

Record the scenario, source data mode, integration mode, expected observable outcome, actual result, and evidence location. Use targeted tests that probe these behaviors. Do not keep rerunning a broad test suite after it passes unless later changes or failures justify it.

At each group checkpoint, show the working result, covered requirement IDs, changed files, evidence, and limitations. Record acceptance of the actual reviewed version; do not mark the group accepted from plan approval or test success. Obtain permission to continue to the named next group. Add accepted files to the accumulated manifest and keep original-repository publication pending until the final build review. Follow [the checkpoint procedure](staged-build-and-git.md). Requested revisions remain in the current group until accepted.

## Check evidence quality and usefulness

For retrieval/assessment workflows, select relevant fixtures with supported facts, a real unknown, an explicit conflict, an inaccessible or wrong-entity source, stale content, and a misleading or unsupported citation. Expected outcomes come from the approved evidence policy, not whatever the implementation returns. Verify that uncertain facts stay uncertain, definitive judgments require their stipulated evidence, and a source-access problem is not reported as a business mismatch.

For comparative assessments, include realistic incomplete or irregular records drawn from the intended sources. Verify that commonly absent optional fields do not suppress otherwise useful ranked results; matching evidence and consequential gaps remain visible; and sparse evidence cannot produce an unexplained advantage. Check provisional ordering or ties against the approved method, and confirm that an item-level failure does not discard independent results when continuation is allowed. Record which expected inputs were actually available, rather than claiming robustness from complete synthetic examples alone.

Exercise the optional reassessment journey: view ranked results and evidence gaps, leave a gap unanswered without losing the initial result, add information to one identified item, explicitly request reassessment, reload, and inspect the revised conclusion/rank and remaining gaps. Check provenance and version history, conflicting new evidence, and the declared scope of any ranking update. The flow must not require an unrelated artifact request or trigger an unrequested action. For a single-item task, omit the ranking checks while retaining evidence and reassessment checks.

When live acceptance is authorized, exercise representative retrieved records through the actual deployed/local reader, extraction, assessment, persistence, and UI. A provider connectivity probe or a successful fictional assessment cannot replace this path. Record candidates found, sources read, records supported, items assessed, unresolved items, and failures with reasons. Check the support for material claims in sampled outputs. Use the same inputs and constraints for comparisons; a small live sample is not an estimate of overall search recall. Zero results may be correct, but unexplained zero results do not establish useful discovery. Do not fabricate a minimum hit count or weaken evidence requirements to pass.

## Check human understanding and visual usability

Walk through the application's principal journeys from the UI, using the intended user's task descriptions rather than implementation identifiers. Include supplying inputs, resolving a question, reading an assessment, and acting on or reviewing it when present. Check that the user can find the action, understand what is requested, enter a valid response, see confirmation, and understand what happens next without reading source code.

Evaluate at least a normal and an uncertain result against the human-question and assessment contracts in [runtime and delivery](runtime-and-delivery.md). Check required/optional fields, meaningful examples, unknown/decline paths, evidence access, and plain explanations of conclusions and scores. Do not treat a submitted JSON object or a clicked button as proof of comprehension.

Inspect rendered desktop and narrow-screen states for clear visual hierarchy, readable type/contrast, consistent spacing, reasonable density, focus/keyboard behavior, action visibility, and responsive layout. Fix observed defects and rerun the affected journey. Save concise screenshots and walkthrough evidence. If browser access or the target runtime is unavailable, mark those checks unverified rather than claiming visual or end-to-end acceptance. An agent walkthrough is a usability review, not evidence of testing with actual users; invite the user's feedback and record remaining subjective preferences.

## Completion and final handoff

Call the application working only when its required workflow, tools, selected model, persistence, and UI have been exercised to the extent authorized. If the user declines live testing, credentials are missing, or the selected host cannot reach a required service, clearly report the remaining unverified integration and describe the deliverable as a prototype or partially connected application. A simulated demonstration is still useful, but its status must be accurate.

Every required ledger item must be verified or explicitly reported as a gap. Reconcile the group's recorded acceptance with the current implementation; material later changes need renewed review of affected behavior. A deferred feature requires a user-approved scope decision and retains its impact; it cannot disappear under an assumed MVP. Distinguish deployment status from functional completeness, source quality, UI acceptance and original-repository publication. Fix implementation defects under the existing approved behavior; seek a targeted user decision for changed business rules or other material scope/access changes. Keep the stage summary current instead of relying on a later append-only note to contradict an earlier 'completed' or 'pending' label.

### Prepare the final-state engineering handoff

Produce `docs/development-handoff.md` under the application root, or the established equivalent, from [the development handoff template](../assets/development-handoff-template.md). This is a separate deliverable from the internal build record. It must let a system engineer understand, reproduce, operate, and assess the delivered system without reconstructing the build conversation. Record final choices and consequential reasons, not a chronological change log, every modified file, abandoned alternatives, or approval transcripts.

Populate it from the final source/configuration and observed evidence, using the template for architecture and entry points, dependency/runtime versions, task-to-model configuration, tools and authentication references, documents/data/persistence, workflow authority and human review, operating/deployment/recovery procedures, verification limits, and prioritized engineering review items. Tailor details to the chosen runtime; do not prescribe services the system does not use. Treat missing setup and unverified behavior as explicit gaps rather than completed configuration. A review item needs a concrete component/file/configuration, impact, next check or action, pass criterion, status, and owner or “unassigned”; distinguish release blockers from optional improvements. Do not invent production readiness or engineer sign-off.

Before delivery, check that referenced files and entry points exist, configuration names match their consumers, setup commands match the selected environment, and claims about models, tools, storage, deployment, and verification agree with the evidence. Identify the implementation/tested revision or local hashes and any material uncommitted differences. Record a deployed revision only when verified; this document need not contain its own publication commit. Link detailed operating/test records instead of duplicating them. Do not run additional live transactions, paid calls, deployments, or recovery operations merely to fill the document; mark unperformed checks and their next steps.

Prepare the handoff before the final GitHub approval so it is part of the reviewed artifact set. Keep credentials and private records out; where full operational detail is unsuitable for the repository audience, retain an access-controlled copy and prepare an approved safe summary. Report publication and deployment receipts separately after those actions; reconcile material later runtime changes into the handoff within the authorized publication scope. Deliver a clearly labeled handoff for a partial build too, preserving its unresolved items. Internal history remains available separately when authorized; it is not required handoff content.

Deliver:

1. For a local app, its local URL, easy launcher, one-time setup and start/reopen/stop instructions, local data/output locations, and internet/API or other runtime dependencies; otherwise the confirmed deployed Sites/GitHub Pages URL and required external service locations.
2. A short description of what the user can test, which data/integrations are synthetic or live, and where review or approval is required.
3. A direct link to the completed development handoff, including finalized setup and the prioritized system-engineer review register, plus the safe configuration example and operating instructions. Keep the internal build record and detailed feature acceptance ledger as supporting records with appropriate access; they do not substitute for the handoff.
4. Verification evidence and unresolved setup items, with exact next actions and no credential values.
5. The complete repository artifact manifest and, after authorized final publication, verified commit/branch or PR links for user-confirmed specifications and optional approved revisions, context/reference files, scripts and build files; identify local-only exclusions and any pending push/merge/deployment separately.

At the final checkpoint, obtain approval for the complete reviewed GitHub change set, then publish and verify the remote commits and file contents. An explicit earlier push request uses the same exact-file approval and read-back rules. Do not substitute a Site deployment or local commit for publication to the original GitHub repo. If final publication is declined or blocked, retain the changes and report the exact outstanding action. Do not merge, widen access, or start a scheduler without authorization for that action. Preserve the user's source documents, including confirmed specifications and optional approved revisions. Identify the confirmed design and implementation baselines in the development handoff and verify their alignment. Keep source-file diffs and historical changes in Git/the internal build record; the final handoff does not need to enumerate them.
