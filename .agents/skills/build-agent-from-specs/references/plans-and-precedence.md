# The plans and their precedence

Read this reference at the start of a build, before Stage 1. BUS 4498 students write their agent's plans with the BUS 4498 Agent Builder Kit and keep them in the agent's `runtime/` folder (for example `our_team_agent/runtime/`). The hosting, memory, and permission plans come first; the test plan is written once the agent runs. The plans record decisions made after the original specifications were written, so they are the current standard.

## The files

| Plan | Rules file beside it | What it decides |
|---|---|---|
| `runtime/hosting-plan.md` | `runtime/hosting-rules.md` | The GitHub repository, the agent's folder (often `our_team_agent`, but use the name the plan gives), and the Supabase project; the owner and teammate; what the agent does; the tasks (either "use the tasks in our task specifications" or a task list that replaces them); who can see or change what; each external tool or application, with what the agent does with it (reads, writes, sends), the most sensitive data it touches, and how it connects; files people upload |
| `runtime/memory-plan.md` | `runtime/memory-rules.md` | What the agent must know or remember, sorted into knowledge it reads, what happened, and lessons it learns; what the agent learns from; what must never happen twice |
| `runtime/permissions-plan.md` | `runtime/permission-rules.md` | The owner; the five categories: May (on its own), May with a limit, Ask first (hold for a person), Never (each with where it is enforced: code, a database rule, or both), Who signs off; the off switch; how mistakes are reported |
| `runtime/test-plan.md` (once the agent runs) | `runtime/permission-rules.md`, rule 10 | In the final's HANDOFF.md format: *How to test* (app link, test login, steps to run a case, where to see the result, how to reset) and *Test cases*: five normal cases (N1–N5) and three edge or must-escalate cases (E1–E3), each with the feature it shows, the exact input (one value per field, or a file in `test-data/`), the steps, the expected result written as what must happen, and a test-button check (the status the answer must have, and optional words it must include) or *run by hand*. Then *What the agent reads* (the field names and which are files), *Test mode* (the agent's address and the request format), and *Models to compare*: at least two models and the runs per case, with the Kit's latest passes, seconds per case, and cost per case |

If a rules file is missing from `runtime/`, use the copy in `references/plans/` and tell the user it was missing. The copies in this skill and the ones the Kit writes come from the same source; if they differ, prefer the one in the repository and note the difference.

## Collect them

1. Ask the user for the agent's folder and check `runtime/` for the hosting, memory, and permission plans. Name each plan that is present and each that is missing.
2. For a missing plan, ask the user to write it in the Agent Builder Kit and add it to `runtime/`, or to say explicitly that the build should continue without it. Record either choice in the build record. Never invent a plan's contents.
3. Use `test-plan.md` if it is already there. Otherwise ask for it before Stage 7: the user writes it in the Kit's test plan page once the agent runs. Never write the test cases for the user; you may suggest a case they can accept or change.
4. Read every plan and its rules file in full, with the README, `agent/workflow-of-tasks.md`, and the task specifications. Record the files and their hashes or commit.

## Precedence

- **The plans win.** Where a plan and the README, workflow, or task specifications overlap, use the plan. Where they conflict, follow the plan and list the conflict for the user (file, what each says, what you will follow) in the Stage 1 summary. Do not ask the user to re-approve every overlap; a conflict needs a question only when the plans themselves are unclear or contradict each other.
- **Tasks.** If `hosting-plan.md` says to use the tasks in the task specifications, the workflow and task specifications define the tasks. If it lists tasks, that list replaces the tasks in the repository: build the plan's tasks, use a specification's detail only for a task the plan keeps under the same name and only where the plan is silent, and offer to update `agent/workflow-of-tasks.md` and `agent/task-specs/` to match (applied only after the user approves, following the revision procedure in [repository intake](repository-and-logic.md)).
- **Plans among themselves.** The hosting plan decides the project and tools; the memory plan adds records to it; the permission plan limits every action; the test plan defines acceptance. If two plans describe the same record or action differently, ask the user which is right.
- **The confirmed baseline** for this build is the plans plus the confirmed specifications, read together under these rules.

## How each plan feeds the stages

- **Stage 1 (summary and ledger):** summarize the plans with the specifications, and list the conflicts the plans resolve. Add every row of the permission plan to the feature acceptance ledger: each Never needs its enforcement location (code, a database rule, or both; never instructions alone), each Ask first a hold with a plain reason, each Who signs off a human control. Add the test plan's cases when it exists.
- **Stages 2–3 (inputs and tools):** the hosting plan's external tools and applications are the starting tool inventory. Keep the data tier and the read/write/send distinction: a write or send tool needs the check the permission plan names before it acts. Present the tool comparison only for tools the plan leaves open ("Not sure yet").
- **Delivery:** when the hosting plan names a GitHub repository and a Supabase project, the delivery target is GitHub Pages with a Supabase backend; don't reopen the choice. Every team has a Supabase project; if the plan's URL is missing or doesn't match the project you can reach, ask before creating or changing anything.
- **Stage 5 (controller):** build the permission plan into the controller and the database, following `permission-rules.md`: a settings table for switches and numbers a reviewer may change, a Paused off switch, holds for Ask first, code and database rules for each Never (CHECK, UNIQUE, FOREIGN KEY, ON DELETE RESTRICT, a missing grant, row-level security), sign-off as a recorded click, test mode (`dry_run`), and `ms` and `usage` in each answer. Build the memory plan following `memory-rules.md`, including lessons the agent learns only from the trusted outcomes the plan names.
- **Stage 7 (verification and handoff):** every function the test plan's *Where cases go* lists answers `GET` and has test mode (`hosting-rules.md` rule 14), and a new intake function is named `agent`; if the agent has no test mode, build one following `permission-rules.md` rule 10 (`dry_run`; the case's input in the fields *What the agent reads* names, as JSON or as a form when a case attaches a file; an optional `model` from the test plan's *Models to compare* for that run only; and an answer with `status`, `reasons`, `dry_run`, `ms`, and `usage`, with CORS headers on every answer). The Kit's test buttons then run the cases and fill in the plan's table; if the user asks you to run them instead, run every case not marked run by hand, the number of times the plan says, on each model it lists, and record passes out of n, seconds per case, and cost per case. A normal case that fails blocks acceptance. `HANDOFF.md` and `test-data/` come from the Kit's download at the top of the repository; write `HANDOFF.md` from the test plan's first two sections only if it is missing (How to test; Test cases N1–N5 and E1–E3), and check that every `test-data/` file it names exists.
